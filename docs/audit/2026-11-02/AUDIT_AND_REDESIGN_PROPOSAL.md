## Новые требования владельца

- Два административных пространства: супер-администратор платформы и администратор магазина.

Требует отдельного уточнения: границы 50 000 / 100 000; сумма до или после наценки; общий заказ или сумма по каждому магазину; входит ли доставка; применяется ли процент ко всей базе или по ступеням. Пользователь подтвердил именно наценку 3–7%, но не уточнил эти условия.

## 1. Критические дефекты до коммерческого запуска

### SEC-01. Сервер доверяет стоимости заказа из браузера — P0

Файл: `src/app/api/public/orders/route.ts`, поля `materialsTotalDirams`, `deliveryTotalDirams`, `totalDirams` и `items`.

API принимает название, цену и сумму позиции от клиента. Не требует реальных offerId, не пересчитывает стоимость из БД, не проверяет соответствие корзине и сразу подтверждает заказ. В отдельной базе принят заказ на 1 дирам без корзины. Это позволяет подменить коммерческие условия.

Исправление: сервер получает идентификаторы предложений и количества, проверяет публикацию, доступность магазина, минимальную партию и остатки; рассчитывает базовые суммы, наценку и доставку; создаёт заказ и резервы в транзакции. Клиентские суммы используются только для обнаружения изменения цены, не как источник истины.

Приёмка: подмена цены/итога не изменяет серверный расчёт; пустой заказ запрещён; устаревшая цена требует подтверждения; два конкурентных заказа не резервируют один остаток дважды.

### SEC-02. Данные заказа доступны по UUID — P0

Файл: `src/app/orders/[id]/page.tsx`.

Загрузка заказа не проверяет текущего покупателя. UUID не является механизмом авторизации. Воспроизведено чтение адреса синтетического заказа из гостевого контекста.

Исправление: доступ владельцу, уполномоченному сотруднику и соответствующему магазину; гостю — отдельный непредсказуемый отзываемый токен, хранить только хеш. Чужой заказ → 404. Магазин видит только относящиеся к нему позиции и необходимые для исполнения контактные данные.

### ORD-01. Заказ не связан с исполнением магазина — P1

В схеме есть `product_id` и `offer_id`, но обработчик не записывает их из серверной корзины. Нет сущности заказа магазина, рассчитанной наценки, истории статусов и резервирования. Заявленное в корзине автоматическое разделение между поставщиками не реализовано в данном обработчике.

Нужны родительский заказ покупателя и подзаказы магазинов, привязка каждой позиции к магазину/предложению, снимок названия/цены/ставки, согласованный жизненный цикл и аудит.

### ORD-02. Номер заказа случайный; повтор отправки создаёт дубликат — P1

Используется `Math.random()` на 90 тысяч комбинаций, хотя в проекте уже есть атомарный `nextDocNumber`. Нет ключа идемпотентности оформления. Гостевая корзина после заказа фактически не очищается.

Нужны атомарная нумерация, идемпотентность, корректная очистка своей корзины и восстановление после разрыва соединения.

### SEC-03. Разнородная защита изменяющих API — P1

Новые обработчики предложений и заявок вызывают `assertSameOrigin` и `parseJsonBody`; ряд admin/auth/profile-обработчиков использует прямой `request.json()`. В API заказа нет общей схемы zod, origin-проверки и rate limit. `checkPayloadSize` полагается на Content-Length, не проверяя фактический размер прочитанного тела.

Нужно унифицировать защиту, лимиты, коды ошибок и безопасное логирование. Отсутствие вызова origin-проверки само по себе не доказывает эксплуатируемый CSRF: cookie SameSite=Lax уже снижает риск; требуется отдельный негативный тест.

## 2. Две административные панели

### Что существует

Есть `/admin`, `/seller`, роли SUPER_ADMIN, ADMIN, SUPPLIER_OWNER, SUPPLIER_STAFF и служебные роли. `ADMIN` сейчас означает сотрудника платформы с широкими правами, а не администратора магазина. В `/seller` показаны четыре постоянных нуля, полноценной навигации магазина нет. Реализован seller-scoped API предложений, но нет полного UI создания и редактирования товаров магазином.

Не следует просто переименовать существующий ADMIN в администратора магазина: это перенесёт платформенные права магазинам. Нужно сохранить/перенести существующие учётные записи с явным назначением области доступа.

### Предлагаемая модель

| Область | Супер-администратор | Владелец магазина | Сотрудник магазина | Покупатель |
|---|---|---|---|---|
| Магазины и блокировки | Все | Свой профиль | По разрешению | Публичная информация |
| Общий каталог и дерево | Управление | Выбор категории | Выбор категории | Просмотр |
| Товары магазина | Все, модерация | Создание/правка своих | По разрешению | Опубликованные |
| Цены и остатки | Все | Только свои | По разрешению | Итоговые цены |
| Заказы | Все | Только свой подзаказ | По разрешению | Только свои |
| Комиссия платформы | Настройка и аудит | Просмотр своего расчёта | По разрешению | Итог и пояснение |
| Учётные записи | Все с защитой супер-админов | Своя команда | Без управления владельцем | Свой профиль |
| Аналитика | Вся платформа | Только свой магазин | По разрешению | Нет |

Два пространства управления не требуют удалять служебные роли менеджера/логиста: их можно оставить внутри платформенной панели с ограниченными правами. Проверки должны действовать на сервере для чтения, мутаций, экспорта и файлов.

### Панель магазина

Навигация: Обзор → Товары → Заказы → Остатки и цены → Команда → Настройки магазина. Показатели только из БД. Создание товара: категория → динамические характеристики → фото → базовая цена магазина → остаток/минимум/срок → предпросмотр → отправка на модерацию.

Предлагаю общую карточку товара и независимые предложения магазинов — существующая модель products + supplierOffers для этого подходит. Магазин может предложить новый товар; право менять общую опубликованную карточку другого магазина не получает. Правки общего описания требуют модерации, изменения собственных цены и остатка — отдельный сценарий.

### Панель платформы

Обзор с реальными показателями, магазины и подключения, модерация, каталог и справочники характеристик, заказы/подзаказы, заявки, наценка и история её изменений, доставка, пользователи/права, аудит и настройки. Текущая надпись SUPER ADMIN в Workspace задана жёстко даже для других сотрудников — показывать реальную роль.

## 3. Наценка 3–7%

Текущий движок выбирает правила PRODUCT → SUPPLIER → CATEGORY → GLOBAL; без правила добавляет 10%. Это не новая шкала владельца. Нельзя добавить 3–7% поверх существующей публичной наценки: получится двойное начисление.

Предложение для обсуждения: базой служит стоимость товаров по ценам магазинов до наценки и без доставки; ставка определяется по всей корзине и применяется одинаково к её позициям. При иной договорённости база меняется до реализации.

Предлагаемые непересекающиеся диапазоны: `0 < S < 50 000` → 7%; `50 000 ≤ S ≤ 100 000` → 5%; `S > 100 000` → 3%. Это предложение, границы пока не подтверждены владельцем.

Примеры при начислении на всю базу: 40 000 → 2 800 → 42 800 TJS; 75 000 → 3 750 → 78 750; 120 000 → 3 600 → 123 600. Доставка прибавляется отдельно.

Важный эффект: переход от 49 999 к 50 000 снижает итог примерно с 53 498,93 до 52 500 TJS; от 100 000 к 100 001 — со 105 000 до 103 001,03. Это естественное следствие снижения ставки на всю сумму. Нужен осознанный выбор владельца: разрешить такую оптовую скидку либо применять ступенчатый расчёт. Ступенчатый расчёт даст другие суммы, его нельзя внедрять молча.

В карточке нет окончательной суммы корзины. Предлагаю показывать розничную цену с 7% и пояснение об уменьшении наценки при крупном заказе; в корзине — окончательный серверный пересчёт. Формулировку и прозрачность составляющих утвердить отдельно.

Деньги — bigint в дирамах; процент и порядок округления зафиксированы; округление по строкам должно сходиться с итогом. В заказе сохраняются база, ставка, наценка, итог, версия правила и распределение по магазинам. После оформления изменение правил не меняет старый заказ. Отмена/возврат требуют зафиксированного правила перерасчёта.

Тестовые границы: 0; 49 999,99; 50 000; 50 000,01; 99 999,99; 100 000; 100 000,01; несколько магазинов; дробное количество; изменение корзины; частичная отмена.

## 4. Дизайн: наблюдения по реальным экранам

Общее впечатление: коммерческая витрина выглядит как демонстрационный лендинг с повторяющимися иллюстрациями. Полезные основы уже есть: узнаваемый синий акцент, читаемые основные кнопки, цены с единицами и рабочая серверная корзина. Но декоративный первый экран, изображения и длинное оформление оттесняют выбор и покупку товара.

### Главная — P1

- Первый экран занят крупным лозунгом и наклонёнными карточками без цены и полезного выбора. На мобильном поиск не виден в первом экране.
- Главная при 390 px имеет высоту около 11 942 px: 12 категорий и затем товары идут одной длинной колонкой.
- Одинаковый мешок цемента используется для несвязанных разделов. Статистика 200+/12/01 задана вручную.
- «Популярные» товары получаются из обычной выдачи без подтверждённой метрики продаж; это не доказанные хиты.

Предложение: компактный верх с городом/доставкой, заметный поиск, кнопка каталога, корзина со счётчиком и вход по роли. Первый блок: короткое обещание «Стройматериалы из магазинов Таджикистана с доставкой» + спокойная предметная фотография/коллаж + прямой вход в каталог и заявку по списку. Ниже — компактная сетка категорий и доступные товары. Убрать искусственные показатели и декоративную нумерацию, не связанную с выбором покупателя.

### Каталог и фильтры — P1

- Дерево одновременно существует в статическом categories-data.ts и в таблице БД. Админка меняет БД, витрина строит навигацию из статического дерева.
- Обычный seed создаёт 24 прежних категории, хотя витрина показывает новое дерево 319 групп. На чистом стандартном запуске часть новых групп пустая; требуются отдельные скрипты синхронизации.
- Для родителя при отсутствии определения выбираются фильтры первого ребёнка: это не корректная общая схема смешанной категории.
- UI разрешает несколько брендов, но CatalogPage передаёт только `one(params.brand)`.
- Фасеты считают атрибуты после части фильтров, но до наличия/цены и исключения товаров без предложений. Числа могут не соответствовать выдаче. Нет исключения собственного фильтра при пересчёте вариантов.
- Объявленные range/select/boolean рисуются одинаковыми чекбоксами.
- Все активные предложения поставщиков загружаются для расчёта даже для узкой выборки. Фильтрация итоговой цены и пагинация идут в памяти.

Предложение: один управляемый источник дерева и определений характеристик; стабильные ID атрибутов, тип и единицы; динамическая форма магазина из той же схемы. Витрина: крошки, быстрые дочерние категории, фильтры, понятная сортировка, активные условия и сброс. Мобильные фильтры — удобная панель с фокусом, закрытием и числом результатов. Проверить историю браузера и прямые ссылки.

### Карточки и страница товара — P1

- Реальные productImages загружаются сервисом, но новый ProductDetailView игнорирует `images`: три миниатюры показывают одну иллюстрацию.
- Карточки выдачи используют ProductArt, реальные изображения не подключены.
- `isHit`, `isNew` и старая цена вычисляются из индекса выдачи. Бейдж -15% не соответствует формуле старая цена = новая × 1,15: реальная скидка от старой цены около 13%.
- При 390 px карточка товара имеет ширину документа 748 px. Product-info остаётся справа от галереи; нужны корректные мобильные правила сетки и переносы.
- Есть неподтверждённые обещания про НДС, сертификацию и доступные способы оплаты. Эти сведения должны приходить из подтверждённой конфигурации.

Предложение: настоящая фотография, галерея, компактное имя и артикул, ключевые технические параметры, цена за единицу/упаковку, минимальная партия, наличие и срок; понятный продавец и варианты предложений; явный выбор количества; заметная покупка. На телефоне — последовательная колонка и компактная закреплённая зона цены/действия. Характеристики, описание, документы и доставка — доступные вкладки/секции.

### Корзина — P1

Нужны группы по магазинам, цена единицы, количество, наличие, подтверждённая наценка, пересчёт и явное изменение цены. Обещание разделить заказ должно соответствовать серверным подзаказам. Сейчас количество отправляется при каждом изменении поля; нет устойчивой обработки сетевой ошибки и возможности спокойно ввести дробное число.

Предложение: локальный ввод + подтверждение/blur, блокировка только изменяемой позиции, сохранение фокуса, ошибки возле строки, восстановление сети. Отдельно проверить слияние гостевой корзины после входа и конкуренцию нескольких вкладок.

### Оформление — P1

- Покупатель сначала видит семь машин, готовность в процентах, водителей, маршрут и диаграммы. Контакты и адрес находятся значительно ниже.
- Вес считается по словам в названии и искусственно ограничивается минимумом 350 кг; даже один кирпич превращается в 350 кг.
- График использует постоянные «Сегодня, Вт» / «Завтра, Ср». На дату аудита 02.11.2026 это не реальные календарные дни.
- Маршрут, свободная дорога, водитель и статус рейса не подкреплены реальной диспетчеризацией. Встречается чужое имя Bizon TJ.
- При 390 px scrollWidth = 573; блок dispatch-vehicle-showcase шире экрана.
- В 6 видимых контролах нет программно связанных подписей. Нет h1 в заполненном оформлении. Кликабельные div не везде имеют клавиатурный обработчик.

Предложение: Получатель и адрес → способ/дата получения → оплата → проверка заказа. Справа на компьютере — компактный итог; на телефоне — сводка и заметная финальная кнопка. Покупателю доступны «доставка» и «самовывоз»; выбор машины система предлагает как пояснимую рекомендацию, диспетчер подтверждает после заказа. Реальные ограничения веса/габаритов, доступ и разгрузка запрашиваются при необходимости. Нет фиктивного рейса до подтверждения.

### Профиль — P2

Сейчас профиль преимущественно редактирует имя/телефон и показывает сессии. Нужен кабинет покупателя с заказами, деталями/статусом, повтором покупки, адресами, заявками и документами. Основные коммерческие действия важнее таблицы сессий. Сохранение формы должно показывать pending/error/success и обрабатывать обрыв сети.

### Админка — P1/P2

Обзоры платформы/магазина имеют фиктивные нули. Навигация не учитывает права и активный раздел. Нужны реальные очереди: новые заказы, товары на модерации, новые заявки, низкие остатки. Табличная работа: поиск, фильтры, пагинация, массовые действия, экспорт в рамках прав; удобная мобильная альтернатива широким таблицам.

## 6. Подходы к переработке — для выбора

1. **Локальная косметика.** Сохранить страницы и поправить стили. Быстрее, но не решает модель двух панелей и перегруженный путь заказа. Не рекомендую для поставленной цели.
2. **Последовательная переработка существующего проекта — рекомендую.** Сохранить Next.js/Drizzle, авторизацию и полезные модули. Утвердить модель магазина/заказа/наценки, затем общую систему интерфейса и переработать ключевой путь покупки и кабинеты. Позволяет проверять каждый этап и сохранять сделанное.
3. **Новый интерфейс с параллельной миграцией.** Отдельная витрина и кабинеты поверх переработанного API. Максимальная свобода, но больше стоимость, две версии сценариев и риск рассинхронизации. Имеет смысл только при осознанном отказе от текущей UI-базы.

### Рекомендуемое визуальное направление

Предложение автора, ещё не утверждено: современный товарный маркетплейс с белыми карточками, светлым нейтральным фоном, графитовым текстом, одним уверенным синим акцентом и настоящей предметной фотографией. Хорошо читаемая кириллическая типографика; умеренные скругления; компактные коммерческие блоки; анимация только для обратной связи. Общие токены, сетка, поля, кнопки, таблицы, уведомления и состояния для всех трёх пространств.

Существующий логотип/имя STROYHUB сохранить до отдельного решения. Удалить случайные упоминания Bizon и неподтверждённые реквизиты/обещания. Не генерировать отзывы, продажи, скидки, статусы машин и сертификаты для убедительности.

Референсы, просмотренные по официальным источникам:

- [Петрович — каталог](https://petrovich.ru/catalog/): предметная структура строительного ассортимента; ориентир для категорий, наличия и услуг доставки.
- [Петрович — главная](https://petrovich.ru/): ориентир для сочетания товара и строительных услуг.
- [Leroy Merlin — устройство marketplace](https://www.leroymerlin.fr/explication-marketplace.html): явное обозначение продавца, его условий и ответственности; ориентир для многомагазинной модели.

Это источники продуктовых паттернов, не подтверждение визуального копирования. Копировать чужие логотипы, фотографии, тексты и макет целиком не предлагается. Поиск в локальной библиотеке UI дал нерелевантные продукту палитры; эти автоматические предложения не приняты. Визуальное направление выше — самостоятельное предложение на основании экранов и задач проекта.

## 7. Порядок работы после выбора подхода

1. Зафиксировать решения по наценке, магазинам, общей карточке и разделению заказов; оформить спецификацию с критериями приёмки.
2. Закрыть доверие к клиентской цене, доступ к заказам, валидацию и резервы. Добавить негативные/конкурентные тесты.
3. Реализовать полноценную панель магазина и модерацию платформы; не расширять права магазина на всю БД.
4. Подготовить согласованный визуальный образец главной, каталога, товара и checkout на компьютере и телефоне. Показать их вместе, до массовой переделки остальных страниц.
5. Перенести утверждённую систему в компоненты, затем пройти весь сценарий покупки и оба кабинета.
6. Заказы/подзаказы, наценка, документы, уведомления, доставка; потом второстепенные функции.
7. Приёмка: lint/types/tests/build; E2E покупатель/два магазина/супер-админ; 360/390/768/1024/1440 px; клавиатура; реальные фотографии; отсутствие горизонтального переполнения; ошибки сети; резервирование и изменение цены; внешний PostgreSQL; пробный выпуск с откатом.

Критерий презентационной готовности: все показанные действия работают на согласованных данных; нет имитации продаж/статусов, мёртвых кнопок, фиктивных скидок и обрезанного контента. Критерий production-готовности дополнительно включает безопасность, расчёты, восстановление и эксплуатационные проверки.

## Что не завершено этим аудитом

Полное покрытие всех 30 страниц и 40 API, нагрузка, все роли/состояния, безопасность загрузок и импортов, внешний PostgreSQL, восстановление резервной копии, браузерная матрица и production-сборка остаются отдельными проверками. Находки с пометкой «по коду» не выдаются за воспроизведённые. Текущий результат: подтверждённые критические дефекты, обследование основного пути, снимки, карта недостающих функций и предложение направления.
