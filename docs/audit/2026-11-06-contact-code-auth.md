# Актуальная авторизация: SMS / e-mail

Последнее уточнение пользователя заменяет прежний вариант TOTP. Приложение-аутентификатор, резервные ключи и подсказки об их хранении удалены из текущего интерфейса и входа. Двухэтапный пользовательский путь теперь: контакт → одноразовый код. Это вход с подтверждением владения контактом, а не независимая комбинация пароля и TOTP.

## Что реализовано
- Общие страницы входа и регистрации, без выбора роли и без пароля. Переключатель «По телефону / По почте».
- Регистрация требует имя, телефон для связи, согласие с документами; e-mail обязателен при отправке кода на почту. Аккаунт создаётся только после проверки кода и получает роль CUSTOMER. Роли сотрудников и магазина назначаются через существующее управление.
- SMS / e-mail код из шести случайных цифр. Срок действия 5 минут. В БД сохраняется bcrypt-хеш, контакты и ограниченные данные ожидающей регистрации; код не возвращается в API и не попадает в журналы.
- Однократное применение с блокировкой строки БД, максимум 5 неверных попыток; повторный запрос не раньше минуты. Запросы ограничены по получателю и IP. Новый отправленный код аннулирует предыдущие неиспользованные коды контакта.
- Повторная отправка и ошибки видны в форме. Без настроенного канала возвращается 503, шаг «код отправлен» не появляется.
- После проверки: HttpOnly cookie и серверный сеанс на 30 дней, принятие гостевой корзины, переход в нужный кабинет по действующей серверной роли. Заблокированные, удалённые пользователи и изменённые после отправки контакты не допускаются.
- Вход по почте или SMS работает и для существующих аккаунтов: подтверждается именно контакт из записи пользователя. Проверка не создаёт произвольных привилегий.
- Старые password API оставлены для локальных проверок и совместимости, но по умолчанию выключены в production (410). Явный AUTH_LEGACY_PASSWORD_LOGIN=true допускает их временное включение при миграции. Публичный интерфейс их не использует.
- /api/auth/two-factor возвращает 410. Старый /account/security перенаправляет к настройкам профиля. Таблица миграции старого экспериментального TOTP сохранена как история схемы; код чтения её секретов и управления ими удалён. Она не участвует во входе.

## Подключение доставки — пока НЕ выполнено
По выбору пользователя подготовлен серверный адаптер без реального провайдера. Коды не отправляются на настоящие телефоны или почту в локальном превью. Сайт явно сообщает, что канал пока не подключён.

Предусмотрен единый HTTP-шлюз с переменными только на сервере:
- AUTH_SMS_SEND_URL / AUTH_SMS_SEND_TOKEN;
- AUTH_EMAIL_SEND_URL / AUTH_EMAIL_SEND_TOKEN.

Контракт шлюза: POST HTTPS, Authorization: Bearer <server token>, JSON {template:"login_code",recipient:<phone or email>,code:<six digits>,expiresInSeconds:300}. Подтверждение принятия: HTTP 2xx и JSON {accepted:true}. Редиректы запрещены, таймаут 10 секунд. В development допускается только локальный HTTP для испытаний. Произвольный SMTP или API SMS-поставщика не заработает только от указания его адреса: нужен согласованный адаптер под реальный контракт. После выбора поставщиков необходимо подключить конкретный SMS API и SMTP/почтовый API, проверить отправителя и доставляемость. Токены не вводятся в форму и не передаются клиенту.

Принятие сообщения провайдером не доказывает доставку пользователю; для эксплуатационного контроля нужен статус доставки поставщика. В production перед включением нового входа обязательно настроить оба нужных канала и проверить доступ сотрудников/магазинов. Если нужны только SMS или только e-mail, UI должен отражать выбранный доступный канал.
