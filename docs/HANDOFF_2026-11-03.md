## 2. Обязательная логика входа в каталог

Требование пользователя: сначала проходить по каталогу, затем открывать товары.

Обычный путь: `/catalog` → главный раздел → подраздел → конечная товарная группа → сетка товаров → страница товара.

- На `/catalog` показывать карточки основных категорий, а не общий список всех товаров.
- На промежуточном уровне показывать его дочерние категории. Например: «Стройматериалы» → «Смеси» → «Цемент и бетон».

- Хлебные крошки должны содержать каждый уровень и позволять вернуться назад.

## 9. Динамические характеристики и фильтры

- Набор полей формы зависит от конечной категории.
- Родительский раздел не получает свойства первого ребёнка.
- Типы контролов: число/диапазон, логическое значение, выбор из подтверждённого справочника, текст для допустимых дополнительных свойств.
- Основные поля показывать первыми, дополнительные — вторым уровнем.
- В смешанных группах сначала выбирать вид изделия; затем показывать соответствующие параметры.
- При смене вида/категории не сохранять скрытые параметры другого изделия.
- Сервер должен проверять категорию, типы, единицы, дубли ключа/русской подписи и соответствие выбранному виду.
- Витрина строит значения по реальным опубликованным товарам, без выдуманных вариантов.
- Между характеристиками AND, внутри многозначного выбора OR; счётчики фасета считаются без его собственного ограничения.
- Числа сравниваются численно; совместимые единицы нормализуются.
- Одиночные/почти незаполненные неактивные фасеты скрываются; выбранный фильтр можно снять.
- Состояние URL, чипы, сброс, Back/Forward сохраняются.

База этого механизма реализована. Перечни обязательных полей, инженерные пределы и закрытые значения требуют подтверждения реальным ассортиментом; рекомендации Excel нельзя автоматически объявлять проверенной спецификацией каждого товара.

## 13. Оформление и жизненный цикл

- Последовательность: получение/адрес → транспорт/время/разгрузка → контакты → оплата → проверка и отправка.
- На компьютере компактный итог рядом; на телефоне удобная последовательность без переполнения.
- Итоги, цены, наличие, минимальные количества и резервы проверяет сервер.
- Повтор отправки заказа защищён идемпотентностью.
- Уже реализованы платформенные переходы NEW → CONFIRMED → DISPATCHED → DELIVERED и отмена из NEW/CONFIRMED.
- Отмена возвращает резерв один раз; получение списывает остаток и снимает резерв один раз; конфликт откатывает операцию.
- Действия защищены `orders:manage` и записываются в аудит.
- Частичная обработка по магазинам, возвраты, автоматический срок истечения резерва и реальное назначение рейса ещё требуют завершения.
- Если доставка не рассчитана подтверждённым тарифом, явно отделять её от суммы материалов.
- Реальный эквайринг/выдача оплаченного счёта не подключены; «запросить счёт» не равно «счёт сформирован/оплачен».

## 14. Роли и панели

- Панель платформы `/admin`: супер-администратор видит и управляет всем в рамках предусмотренных разрешений.
- Панель магазина `/seller`: владелец/сотрудники работают только со своим магазином.
- Магазин добавляет свои товары, фото и характеристики, редактирует свои предложения, цену и остаток.
- Новая карточка/изменения контента идут на модерацию; общий товар нескольких магазинов нельзя дать одному магазину произвольно менять.
- Сервер сам определяет магазин по членству пользователя; `supplierId` из браузера не является основанием доступа.
- Владелец управляет приглашениями команды, сотрудники не получают лишние права.
- Магазин не видит чужие предложения, позиции и внутреннюю финансовую информацию.
- У платформы — модерация, категории, товары, магазины, пользователи, заказы и аудит.
- Навигация показывает доступные пункты и выделяет активный раздел.
- Формы товара должны использовать одну и ту же модель категорий/атрибутов в обеих панелях.

Эти основы уже реализованы. Полноценный процесс исполнения подзаказов каждым магазином ещё не завершён.

## 15. Наценка платформы

Требование: 3–7% наценки к цене магазина. Сейчас в коде:

- база меньше 50 000 TJS — 7%;
- база от 50 000 до 100 000 TJS включительно — 5%;
- свыше 100 000 TJS — 3%.

Текущая интерпретация: база до наценки, общая стоимость товаров всей корзины, без доставки; ставка применяется ко всей базе. Порог по всему заказу/по магазину, точные границы и бухгалтерское оформление отдельно с владельцем не были полностью уточнены.

Не накладывать новую наценку поверх старых 7/10%. Сохранять расчёт и ставку в заказе; использовать точные денежные вычисления. Для единичной карточки можно показывать оценку с 7%, но в корзине итог должен пересчитываться по объёму заказа.

Основной файл: `src/modules/pricing/order-markup.ts`.

## 16. Тексты и качество интерфейса

- Никаких служебных заметок «от ИИ», шаблонных лозунгов и объяснений реализации внутри покупательского пути.
- Не создавать отзывы, скидки, продажи, сертификаты, наличие, водителей и обещания доставки для убедительности.
- Русские подписи, правильные склонения, единицы, читаемые суммы в сомони.
- Видимые состояния loading/error/success/disabled; сетевой сбой не оставляет кнопку навсегда заблокированной.
- Достаточные размеры касания, контраст, клавиатура, видимый focus, отсутствие горизонтального переполнения.
- Профиль покупателя: заказы, их детали/статусы, заявки и редактирование данных с понятными результатами сохранения.

4. Обновить E2E под новое требование: `/catalog` теперь содержит категории. В `tests/e2e/catalog.spec.ts` ещё осталось старое ожидание 24 товаров на корневой странице; тест нужно исправить под новый путь, а не возвращать ради него старый интерфейс.
