### 0.3. Общие соглашения проекта (применяются ко всем разделам)

**Роли.**

| Роль | Описание |
|---|---|
| Гость | Неавторизованный посетитель |
| Покупатель | Авторизованный пользователь с записью в `customers` |
| Менеджер | `SALES_MANAGER`, `PROCUREMENT_MANAGER` |

**Деньги.** ✅ Валюта TJS. В БД хранятся в дирамах (`bigint`), 1 TJS = 100 дирам. 🆕 Ввод в UI — в сомони с запятой/точкой, максимум 2 знака; перевод в дирамы без плавающей арифметики (через строку или целочисленное умножение). Отрицательные значения запрещены.

**Телефон.** ✅ Нормализация к E.164. 🆕 Правила:
- начинается с `+` → оставить только цифры после плюса, длина 8–15;
- 9 цифр без кода страны (например `921234567`) → добавить `+992`;
- начинается с `992` и далее 9 цифр → добавить `+`;
- начинается с `0` + 9 цифр → отбросить `0`, добавить `+992`;
- пробелы, дефисы, скобки удаляются;
- всё остальное → ошибка валидации `phone_invalid`.

**E-mail.** ✅ Нормализация. 🆕 trim + нижний регистр, не более 254 символов, проверка по zod `.email()`.

**Даты.** 🆕 В БД — UTC (`timestamptz`); `date` — без времени. В интерфейсе показывать в часовом поясе Asia/Dushanbe (UTC+5).

**Формат ошибок API.** 🆕 (сверить с существующим форматом проекта; если он уже есть — использовать его)

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Проверьте введённые данные",
    "fields": { "contactPhone": "phone_invalid" }
  }
}
```

| HTTP | Когда |
|---|---|
| 400 | Ошибка валидации |
| 401 | Нет авторизации там, где она нужна |
| 403 | Нет права |
| 404 | Объект не найден (или чужой — чтобы не раскрывать существование) |
| 409 | Конфликт версий (оптимистичная блокировка) |
| 429 | Превышен rate limit; заголовок `Retry-After` в секундах |
| 500 | Внутренняя ошибка; тело — без деталей, детали только в логах |

**Аудит.** ✅ Журнал аудита уже существует (событие `referral.linked`). 🆕 Новые события перечислены в п. 8.4.

**i18n.** ✅ Все тексты — через `src/i18n/ru.ts`. 🆕 Строки валидации и сообщения об ошибках — тоже через ключи, не хардкод. Таджикский перевод — отдельная задача; ключи проектируются так, чтобы перевод не требовал правок кода.

**Rate limit.** 🆕 Определяется по IP клиента. За reverse proxy IP брать из доверенного заголовка (`X-Forwarded-For`, первый адрес), и только если запрос пришёл от доверенного прокси. Хранилище счётчиков — то же, что уже используется в проекте для других лимитов.

### 1.8. Версионирование соглашения 🆕 (рекомендуется, ❓ требует решения)

Проблема: сейчас хранится только время. Если текст изменится, доказать, какой именно текст принял пользователь, будет нельзя.

**Минимальный вариант.** В коде — константа `TERMS_VERSION = '2026-10-30'`. В `users` — колонка `terms_version text`. При регистрации записывается значение константы. Старый текст сохраняется в репозитории (папка `docs/terms/` с датой в имени файла).

**Расширенный вариант (не обязателен сейчас).** При смене версии показывать залогиненному пользователю блокирующий экран «Мы обновили условия» с чекбоксом и обновлять `terms_accepted_at` и `terms_version`.

### 1.9. Миграция существующих пользователей ✅ + ❓

`drizzle/0037_terms_accepted.sql` в текущем виде:

```sql
ALTER TABLE "users" ADD COLUMN "terms_accepted_at" timestamp with time zone;
UPDATE "users" SET "terms_accepted_at" = "created_at" WHERE "deleted_at" IS NULL;
```

Что делает: проставляет «принятие» задним числом по дате регистрации. Риск: пользователи на самом деле соглашение не принимали (его не было), и такая запись может быть использована против платформы как недостоверная.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A.** Оставить как есть | Все поля заполнены, нет блокирующих экранов | Фиктивная запись о принятии |
| **B.** Оставить `NULL` у существующих; при следующем входе показать экран принятия | Юридически чисто | Нужен дополнительный экран и логика (п. 1.8, расширенный вариант) |
| **C.** Как A, но писать в аудит пометку «backfill, принятие не подтверждено пользователем» | Простая реализация, честная история | Остаётся неоднозначность |

Рекомендация 🆕: **B**, если соглашение действительно важно для юридической защиты; иначе **C**.

### 2.6. Жизненный цикл ✅ + 🆕

```
NEW ──► IN_REVIEW ──► AVAILABLE
  │          │
  │          └──────► UNAVAILABLE
  │
  └─ (прямой переход NEW → AVAILABLE / UNAVAILABLE допустим)

CANCELLED — отмена покупателем (в enum, не реализовано)
```

| Из \ В | NEW | IN_REVIEW | AVAILABLE | UNAVAILABLE | CANCELLED |
|---|---|---|---|---|---|
| NEW | — | ✅ | 🆕 да | 🆕 да | 🆕 (будущее) |
| IN_REVIEW | нет | да (обновление ответа) | ✅ | ✅ | 🆕 (будущее) |
| AVAILABLE | нет | 🆕 да (переоткрыть) | да (обновить данные) | 🆕 да | нет |
| UNAVAILABLE | нет | 🆕 да (переоткрыть) | 🆕 да | да (обновить данные) | нет |
| CANCELLED | нет | нет | нет | нет | — |

Правила 🆕:
- менеджер не может установить статус `NEW` или `CANCELLED`;
- при `AVAILABLE` и `UNAVAILABLE` комментарий обязателен (покупателю нужно объяснение);
- при `AVAILABLE` желательно указать цену или срок; без них показывать предупреждение, но не блокировать ❓;
- `resolved_product_id` допускается только при `AVAILABLE`.

### 2.10. API ✅ + 🆕

Примеры иллюстративны: имена полей нужно сверить с `product-request-schemas.ts`.

#### `POST /api/product-requests` — создать (auth: optional)

Запрос:
```json
{
  "productName": "Арматура А500С Ø12",
  "description": "Длина 11,7 м, с сертификатом",
  "quantity": 5.5,
  "unit": "т",
  "requiredDate": "2026-12-15",
  "contactName": "Рустам",
  "contactPhone": "921234567",
  "contactEmail": "rustam@example.com"
}
```
Ответ `201`:
```json
{ "id": "uuid", "number": "PRQ-0001", "status": "NEW", "createdAt": "2026-10-31T09:00:00Z" }
```
Ошибки: `400` (валидация), `429` (лимит).
🆕 В ответе гостю **не** возвращаются контактные данные других пользователей и внутренние поля (`assigned_to`, `version`).

#### `GET /api/product-requests` — список (право `product_requests:manage`)

Параметры 🆕: `status`, `q`, `page` (≥1), `pageSize` (1–100, по умолчанию 25), `sort`.
Ответ: `{ "items": [...], "total": 123, "page": 1, "pageSize": 25 }`.

#### `GET /api/product-requests/[id]` — детали (право `product_requests:manage`)

Ответ: полная запись, включая историю изменений 🆕. `404`, если не найдена.

#### `PATCH /api/product-requests/[id]` — ответ (право `product_requests:manage`)

Запрос:
```json
{
  "status": "AVAILABLE",
  "responseNote": "Поставим со склада в Душанбе, сертификат прилагается",
  "estimatedPriceDirams": "850000",
  "estimatedDeliveryDays": 5,
  "resolvedProductId": null,
  "version": 3
}
```
🆕 `estimatedPriceDirams` передаётся **строкой** (BigInt не сериализуется в JSON стандартными средствами; закрывает F12). Если API принимает сомони — это нужно явно указать и применять единый способ перевода в дирамы.
Ответы: `200` с обновлённой записью; `400`; `403`; `404`; `409` (устаревшая `version`).

### 2.12. Отмена заявки покупателем (CANCELLED) 🆕 — решение по F3

Вариант 1 (минимальный): убрать `CANCELLED` из enum до реализации.
Вариант 2: реализовать. Тогда:
- кнопка «Отменить заявку» в кабинете, доступна при статусах `NEW`, `IN_REVIEW`;
- подтверждение в диалоге;
- `PATCH /api/account/requests/[id]` с `{ "action": "cancel" }`;
- причина отмены — необязательное поле;
- менеджер видит заявку с пометкой «Отменена покупателем»; редактирование ответа блокируется.

### 2.13. Уведомления ❓

Сейчас покупатель узнаёт об ответе, только зайдя в кабинет; гость — не узнаёт вообще.

| Вариант | Описание |
|---|---|

| ID | Требование |

| REF-06 | 🆕 После 5 неудачных попыток — ошибка 500 с записью в лог (вероятность исчезающе мала, но поведение должно быть определено) |

### 3.7. Привязка при регистрации ✅ + 🆕

`registerCustomer`:

1. Создаются `users` и `customers` ✅.
2. Если пришёл `refCode` ✅:
   - нормализация: trim + upper-case;
   - поиск `customers` с таким `referral_code` и не удалённого (`deleted_at IS NULL`);
   - если найден и это не тот же customer:
     - `referred_by_customer_id` ← id пригласившего;
     - `source` ← `'referral'`;
     - создаётся запись `referral_bonuses` со статусом `PENDING`;
     - аудит `referral.linked`.
3. Невалидный или несуществующий код игнорируется молча, регистрация проходит ✅.

### 3.8. Защита от злоупотреблений 🆕 (закрывает F9; полностью зависит от решения #45)

## 4. ИИ-агент для автогенерации КП

### 4.1. Статус ✅

**Отложено.** Блокирующие решения:
1. выбор ИИ-провайдера (Claude API, OpenAI, локальная модель);
2. API-ключи;
3. бюджет на запросы;
4. шаблон промпта и состав контекста.

Раздел ниже — не реализация, а **полное проектное задание**, чтобы после решений по п. 1–4 можно было приступать к работе.

### 4.2. Цель и принципы 🆕

**Цель.** Сократить время менеджера на подготовку коммерческого предложения: система собирает черновик КП из истории заказов, каталога и параметров клиента.

**Принципы (неотрицаемые):**

| ID | Принцип |
|---|---|
| AI-01 | ✅ Менеджер проверяет и подтверждает КП перед отправкой клиенту. Автоотправка запрещена |
| AI-02 | ✅ Внутренние цены (закупка, маржа) **никогда** не передаются в контекст ИИ |
| AI-03 | 🆕 **Цены в КП рассчитывает система по существующему ценовому движку, а не модель.** Модель предлагает позиции, количества и замены; цены и суммы подставляет код |
| AI-04 | 🆕 Модель может предлагать только товары, которые существуют в каталоге (проверка по ID/артикулу); выдуманные позиции отбрасываются |
| AI-05 | 🆕 Любое обращение к ИИ журналируется (кто запустил, какой клиент, что передано — без секретов, что получено) |
| AI-06 | 🆕 При недоступности ИИ-провайдера менеджер может создать КП вручную; система не блокируется |

### 4.3. Пользователи и сценарии 🆕

| ID | Роль | Сценарий |
|---|---|---|
| S4.1 | Менеджер | На карточке клиента или заказа нажимает «Сгенерировать КП» |
| S4.2 | Менеджер | Видит черновик: позиции, количества, замены с пояснением, итог |
| S4.3 | Менеджер | Редактирует позиции, удаляет, добавляет, меняет количество |
| S4.4 | Менеджер | Подтверждает КП → документ переходит в «Готово к отправке» |
| S4.5 | Менеджер | Отклоняет черновик с причиной (для оценки качества) |
| S4.6 | Администратор | Видит расход токенов и стоимость, лимиты, журнал запросов |

### 4.4. Архитектура ✅ + 🆕

Модуль: `src/modules/ai/quote-generator.ts` ✅.

```
Менеджер ──► API (/api/ai/quotes) ──► сборщик контекста ──► провайдер ИИ
                                          │                     │
                                   (белый список полей)         ▼
                                                        ответ в JSON-схеме
                                                                │
                                           валидатор ◄──────────┘
                                                │
                              ценовой движок (цены, суммы, НДС)
                                                │
                                      черновик КП (DRAFT_AI)
                                                │
                                   проверка менеджером → подтверждение
```

**Слои**

| Слой | Ответственность |
|---|---|
| `context-builder` | Собирает входные данные **только из белого списка** полей |
| `provider` (интерфейс) | `generate(prompt, schema): Promise<result>`; реализации для выбранного провайдера; позволяет заменить провайдера без изменения остального кода |
| `validator` | Проверяет, что ответ соответствует схеме, товары существуют, количества положительные, нет недопустимых полей |
| `pricing` | Назначает цены и суммы через существующий механизм |
| `quote-service` | Сохраняет черновик, статусы, аудит |

### 4.5. Данные контекста 🆕

**Можно передавать (белый список):**

| Группа | Поля |
|---|---|
| Клиент | Тип (физ/юр лицо), регион, сегмент; **без** ФИО, телефона, e-mail, адреса — их ИИ не нужны |
| История | Для прошлых заказов — SKU, наименование, количество, дата; **без цен закупки и маржи**; отпускные цены — только если политика это допускает ❓ |
| Каталог | SKU, наименование, единица, категория, характеристики, наличие (булево или диапазон), без закупочных цен |
| Запрос | Текст/список нужных товаров, который ввёл менеджер или клиент |
| Правила | Правила замен (какие категории взаимозаменяемы); правила наценки описываются **для кода**, а не передаются как числа |

**Нельзя передавать:** закупочные цены, маржу, коэффициенты наценки, данные поставщиков (условия, скидки), персональные данные (телефон, e-mail, адрес, документы), платёжные данные, внутренние комментарии сотрудников.

Реализация запрета 🆕: контекст строится из явных DTO с белым списком; типы не допускают передачу «целой строки из БД»; автоматический тест проверяет, что в сформированном промпте нет запрещённых значений (например, подстановка тестовой закупочной цены и поиск её в тексте).

### 4.6. Промпт и формат ответа 🆕

**Структура промпта**
1. Роль и ограничения (кто ты, что нельзя).
2. Правила: использовать только товары из переданного каталога; не придумывать цены; если товара нет — вернуть в `unmatched`.
3. Данные клиента (обезличенные).
4. История.
5. Релевантные товары (результат предварительного отбора, а не весь каталог).
6. Запрос.
7. Требуемая JSON-схема ответа.

**Формат ответа**

```json
{
  "items": [
    { "sku": "ARM-A500-12", "quantity": 5.5, "unit": "т", "reason": "Входит в запрос" }
  ],
  "substitutions": [
    { "requestedText": "арматура 12", "suggestedSku": "ARM-A500-12", "explanation": "Совпадает по диаметру и классу" }
  ],
  "unmatched": [
    { "requestedText": "уголок 75×75", "note": "В каталоге не найден" }
  ],
  "notes": "Краткий комментарий для менеджера"
}
```

Валидация ответа 🆕:
- ответ — валидный JSON, соответствует схеме;
- каждый `sku` существует и не удалён;
- `quantity > 0`;
- нет цен и скидок (если модель их вернула — игнорируются);
- длина текстовых полей ограничена; текст экранируется при выводе.

### 4.7. Защита от инъекций и утечек 🆕

| Угроза | Мера |
|---|---|
| Prompt injection через текст клиента (заявки, комментарии, описание) | Пользовательский текст передаётся как данные в отдельном блоке с явной пометкой «данные, не инструкции»; ответ строго валидируется; модель не имеет доступа к инструментам и БД |
| Утечка внутренних данных | Белый список (п. 4.5), тест на отсутствие запрещённых значений |
| Выдуманные позиции/цены | AI-03, AI-04 |
| Раскрытие ключей API | Ключ только в переменных окружения сервера, не попадает в клиентский код и логи |
| Чрезмерные расходы | Лимиты: запросов на менеджера в час/сутки, максимальный размер контекста, максимальное число токенов ответа, ежемесячный потолок бюджета с отключением функции при превышении |
| Передача ПДн за рубеж | Обезличивание перед отправкой; ❓ юридическая проверка, допустима ли передача в выбранную юрисдикцию |

### 4.8. Состояния КП 🆕

```
DRAFT_AI ──► IN_EDIT ──► APPROVED ──► SENT
    │                        
    └──► REJECTED
```

| Статус | Значение |
|---|---|
| `DRAFT_AI` | Создан ИИ, не просмотрен |
| `IN_EDIT` | Менеджер редактирует |
| `APPROVED` | Подтверждён менеджером (с отметкой «кем» и «когда») |
| `SENT` | Отправлен клиенту |
| `REJECTED` | Отклонён менеджером; обязательна причина |

Для каждого черновика хранится: кто инициировал, версия промпта, провайдер и модель, число токенов, стоимость, время, что изменил менеджер (разница между ИИ-версией и итоговой) — для оценки качества.

### 5.4. Предлагаемая миграция `0040_integrity_hardening.sql` 🆕

```sql
-- Версия соглашения
ALTER TABLE "users" ADD COLUMN IF NOT EXISTS "terms_version" text;

-- Целостность заявок
ALTER TABLE "product_requests"
  ADD CONSTRAINT "product_requests_quantity_pos" CHECK ("quantity" IS NULL OR "quantity" > 0),
  ADD CONSTRAINT "product_requests_price_nonneg" CHECK ("estimated_price_dirams" IS NULL OR "estimated_price_dirams" >= 0),
  ADD CONSTRAINT "product_requests_days_nonneg" CHECK ("estimated_delivery_days" IS NULL OR "estimated_delivery_days" >= 0);

-- Целостность рефералов
ALTER TABLE "customers"
  ADD CONSTRAINT "customers_no_self_referral" CHECK ("referred_by_customer_id" IS NULL OR "referred_by_customer_id" <> "id");
CREATE INDEX IF NOT EXISTS "customers_referred_by_idx" ON "customers" ("referred_by_customer_id");

ALTER TABLE "referral_bonuses"
  ADD CONSTRAINT "referral_bonuses_no_self" CHECK ("referrer_customer_id" <> "referred_customer_id"),
  ADD CONSTRAINT "referral_bonuses_amount_nonneg" CHECK ("bonus_amount_dirams" IS NULL OR "bonus_amount_dirams" >= 0);
-- Уникальность связи применять только после решения #45 (см. п. 3.12):
-- CREATE UNIQUE INDEX "referral_bonuses_referred_uq" ON "referral_bonuses" ("referred_customer_id");
```

Перед добавлением ограничений проверить существующие данные запросами на нарушения, иначе миграция упадёт.

### 5.5. Требования к миграциям 🆕

| ID | Требование |
|---|---|
| DB-01 | Применять в порядке 0037 → 0038 → 0039 → (0040) |
| DB-02 | Каждая миграция идемпотентна (`IF NOT EXISTS`, где возможно) |
| DB-03 | Для каждой миграции — описание отката (ручной SQL) в `docs/` |
| DB-04 | Перед применением на production — резервная копия БД и пробный прогон на копии |

## 8. Нефункциональные требования 🆕

### 8.2. Надёжность
- Транзакции в регистрации, создании заявки, ответе менеджера.
- Повторный запрос после обрыва соединения не создаёт дубли (PRQ-08).

### 8.3. Безопасность
- Все права проверяются на сервере.
- Rate limit на публичные POST (заявки; рекомендуется и на регистрацию) ✅/🆕.
- Валидация входа через zod на каждом эндпоинте.
- Экранирование пользовательского текста.
- Заголовки безопасности (CSP, `X-Content-Type-Options`, `Referrer-Policy`) — по общей политике проекта.
- Логи не содержат полных телефонов, e-mail и токенов.

### 8.4. Журнал аудита

- Все поля форм имеют связанные `<label>`.

- Контраст по WCAG AA.
- Страницы управляются клавиатурой.
