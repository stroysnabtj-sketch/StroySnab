# Резервные копии PostgreSQL StroySnab

Сервис Railway `StroySnab-backup` запускается ежедневно в 03:00 по Душанбе (`0 22 * * *` UTC) и завершается после выполнения.

1. `pg_dump` PostgreSQL 18 читает рабочую базу в согласованном снимке.
2. Полное восстановление проверяется в отдельной временной локальной базе контейнера.
3. Дамп загружается в закрытый бакет `stroysnab-db-backups` Railway.
4. Загруженный файл скачивается и проверяется по размеру и SHA-256.
5. Сохраняется JSON-манифест с результатом проверки. Только после этого удаляются полные пары старых файлов сверх последних 30 копий.

Успешный запуск завершается кодом 0 и записью `"backup": "verified"` в Deployment Logs. Ошибка завершается кодом 1. После изменения пароля базы повторный ручной запуск обязателен: подключение использует ссылку `${{Postgres.DATABASE_URL}}`.

## Где смотреть

- Railway → `StroySnab-backup` → Deployments / Logs: результаты и ошибки.
- Railway → `StroySnab-backup` → Settings → Cron Schedule: расписание.
- Закрытый бакет `stroysnab-db-backups`: файлы `postgres/stroysnab-*.dump` и соответствующие `.dump.json`.
- Для внеплановой копии запустить сервис вручную через Deploy/Redeploy. Не менять переменные основного сайта или Postgres.

## Восстановление

Восстанавливать сначала в **новую тестовую базу**, никогда не проверять восстановление поверх рабочей базы.

1. Скачать выбранный `.dump` и соседний `.dump.json` через S3-клиент с ключами бакета. Не публиковать файлы или ключи.
2. Сверить размер и SHA-256 дампа с JSON-манифестом.
3. Использовать клиент PostgreSQL 18. Указать параметры **новой** базы переменными `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`.
4. Выполнить `pg_restore --exit-on-error --no-owner --no-acl --dbname=NEW_DATABASE selected.dump`, подставив имя новой базы.
5. Проверить пользователей, товары, заявки и заказы на отдельном тестовом экземпляре приложения. Только после проверки планировать переключение рабочего сайта.

## Переменные отдельного сервиса

`DATABASE_URL`, `BACKUP_S3_ENDPOINT`, `BACKUP_S3_BUCKET`, `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY`, `BACKUP_S3_REGION`, `BACKUP_KEEP=30`.

Секреты задаются только в Railway, в репозитории их нет. Бакет закрытый, доступ к файлам только по S3-ключам. База и бакет находятся у одного провайдера Railway; это не независимая копия в Cloudflare R2. Фотографии из R2 этот процесс не копирует. Хранение и кратковременный запуск тарифицируются Railway по использованию.
